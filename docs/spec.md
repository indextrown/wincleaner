# WinCleaner 사양서

> Windows 디스크 청소 · 메모리 관리 · 시스템 최적화 통합 프로그램
>
> 작성일: 2026-10-25 · 대상 OS: Windows 10 22H2, Windows 11

---

## 1. 배경과 목표

### 1.1 배경

오래 쓴 Windows PC에 불필요한 파일과 시작 프로그램이 쌓이면서 점점 느려지고 있다. 2026-10-25 기준 개발 PC 상태는 다음과 같다.

| 항목 | 상태 | 판단 |
|---|---|---|
| C: | 206.3GB 사용 / **16.6GB 여유 (약 7%)** | 가장 시급하다. 여유 공간이 10~15% 밑으로 내려가면 업데이트, 페이지 파일, 임시 파일 처리 때문에 체감 속도가 떨어진다 |
| D: | 706.3GB 여유 | 큰 파일과 사용자 폴더를 옮길 곳 |
| RAM | 15.9GB 중 6.8GB 여유 | 현재 병목이 아니다 |

참고: Windows 10 22H2는 2025-10-14에 지원이 끝났다. 프로그램은 Windows 10과 11 모두에서 동작해야 한다.

### 1.2 목표

1. C: 드라이브 여유 공간을 **안전하게** 확보한다.
2. 부팅과 체감 속도를 떨어뜨리는 설정(시작 프로그램 등)을 정리한다.
3. 메모리를 많이 쓰는 원인을 보여 주고, 필요할 때만 수동으로 정리한다.
4. 모든 변경은 미리보기를 거치고, 되돌릴 수 있어야 한다.

### 1.3 우선순위

디스크 청소 → 시작 프로그램·시스템 최적화 → 메모리

## 2. 기술 스택

| 항목 | 선택 | 이유 |
|---|---|---|
| 언어·런타임 | C# / .NET 10 (LTS) | Windows API, 레지스트리, WMI, 서비스, 작업 스케줄러를 직접 다룰 수 있다. .NET 8은 2026-11에 지원이 끝난다 |
| UI | WPF + MVVM (CommunityToolkit.Mvvm) | Windows 전용 데스크톱 앱에 가장 성숙한 선택 |
| 테스트 | xUnit | |
| 배포 | exe 단일 파일 | 설치 없이 실행 |

검토 후 제외한 대안:

- **Python**: exe로 묶으면 백신 오탐이 잦고, 시스템 API를 다루기 번거롭다.
- **Electron**: 청소 프로그램이 수백 MB 메모리를 차지하는 모순이 생긴다.

### 2.1 실행 권한

- 매니페스트는 `requireAdministrator`로 둔다. 청소와 최적화 대부분이 시스템 영역(`C:\Windows\Temp`, 서비스, 복원 지점 등)을 다루기 때문이다.
- `longPathAware`를 켠다. 260자가 넘는 깊은 경로의 임시 파일도 처리해야 한다.
- 앱 안에서도 관리자 권한인지 다시 확인한다. 관리자가 아니면 시스템 영역 작업을 막고 안내 배너를 보여 준다.
- 개발 중에는 `__COMPAT_LAYER=RunAsInvoker` 환경 변수로 UAC 없이 일반 권한으로 실행해 확인한다.

### 2.2 화면 렌더링

WPF는 기본적으로 GPU로 화면을 그린다. 그런데 개발 PC처럼 원격 접속용 가상 디스플레이(LuminonCore IDDCX)가 함께 있는 환경에서는 하드웨어 렌더링이 실패해 창 안쪽이 하얗게만 나왔다. 화면이 단순한 도구라 성능 차이가 거의 없으므로 `RenderOptions.ProcessRenderMode = RenderMode.SoftwareOnly`로 소프트웨어 렌더링을 쓴다.

## 3. 기능 사양

위험도 기준:

- **낮음**: 지워도 앱이 다시 만드는 파일. 기본으로 선택된다.
- **중간**: 되돌릴 수 없거나 사용자 데이터가 섞일 수 있는 항목. 기본으로 선택되지 않는다.
- **높음**: 시스템 동작이 바뀌는 항목. 기본으로 선택되지 않고 실행 전에 한 번 더 확인한다.

### 3.1 디스크 청소 (`WinCleaner.Cleaning`)

| ID | 대상 | 위치 / 방법 | 조건 | 위험도 |
|---|---|---|---|---|
| `temp.user` | 사용자 임시 파일 | `%TEMP%` | 마지막 수정 후 24시간 지난 파일만 | 낮음 |
| `temp.system` | 시스템 임시 파일 | `C:\Windows\Temp` | 24시간 지난 파일만, 관리자 필요 | 낮음 |
| `wu.download` | Windows Update 다운로드 캐시 | `C:\Windows\SoftwareDistribution\Download` | 7일 지난 파일만, 관리자 필요. 진행 중인 업데이트를 방해하지 않도록 서비스는 멈추지 않고 사용 중인 파일은 건너뜀 | 낮음 |
| `do.cache` | 전송 최적화 캐시 | Delivery Optimization 캐시 폴더 | **6단계로 미룸.** 서비스가 관리하는 캐시라 공식 방법(`Delete-DeliveryOptimizationCache`)으로 정리해야 함 | 낮음 |
| `browser.chrome` / `browser.edge` / `browser.firefox` | 브라우저 캐시 | 각 브라우저 프로필의 Cache, Code Cache, GPUCache | 쿠키·비밀번호·기록은 제외, 브라우저가 실행 중이면 건너뜀 | 낮음 |
| `thumbcache` | 썸네일 캐시 | `%LOCALAPPDATA%\Microsoft\Windows\Explorer\thumbcache_*.db` | 사용 중이면 건너뜀 | 낮음 |
| `wer` | 오류 보고서 | `ProgramData\Microsoft\Windows\WER` | | 낮음 |
| `dumps` | 메모리 덤프 | `C:\Windows\Minidump`, `C:\Windows\MEMORY.DMP`, `C:\Windows\LiveKernelReports`, `%LOCALAPPDATA%\CrashDumps` | 관리자 필요 | 낮음 |
| `recyclebin` | 휴지통 | 각 드라이브의 `$Recycle.Bin\<내 SID>` | **구현됨.** 휴지통 전체를 비우지 않고 스캔한 항목만 지운다. 미리보기에 원래 위치를 보여 준다 | 중간 |
| `dism.component` | 업데이트 잔여 구성 요소 | `DISM /Online /Cleanup-Image /StartComponentCleanup` | 정리 후 이전 업데이트로 되돌릴 수 없음 | 중간 |
| `windows.old` | 이전 Windows 설치 파일 | `C:\Windows.old` | 이전 버전으로 되돌릴 수 없게 됨 | 중간 |
| `hiberfil` | 최대 절전 파일 | — | **최적화 항목 `hibernate`로 옮김 (3.3).** 파일 삭제가 아니라 되돌릴 수 있는 설정 변경이기 때문 | 중간 |

2단계에서 위험도 낮음 항목을 구현했다(`do.cache` 제외). 지운 파일은 휴지통을 거치지 않으므로, 정리하기 전에 이 사실을 확인 창에서 알린다.

자동으로 지우지 않고 목록만 보여 주는 도구:

- **용량 분석·큰 파일 찾기**: 3.1.1 참고 (구현됨).
- **중복 파일 찾기**: 크기 비교 → 해시 비교 순서로 찾는다.
- **D:로 이동**: 사용자가 고른 파일이나 사용자 폴더(다운로드, 동영상 등)를 다른 드라이브로 옮긴다.

### 3.1.1 용량 분석 (`WinCleaner.Cleaning.Analysis`)

무엇이 드라이브를 차지하는지 보여 준다. **읽기만 하고 아무것도 바꾸지 않는다.**

| 기능 | 내용 |
|---|---|
| 폴더별 용량 | 드라이브 아래 모든 폴더 크기를 계산해 큰 순서로 보여 준다. 폴더 이름을 누르면 안으로 들어가고, 경로 표시줄과 "위로" 버튼으로 돌아온다 |
| 가장 큰 파일 | 드라이브 전체에서 가장 큰 파일 200개 |
| 설명 | 자주 보이는 큰 항목(hiberfil.sys, pagefile.sys, WinSxS, Installer, Temp, Windows.old 등)에 무엇이고 지워도 되는지 한 줄 설명을 붙인다 (`KnownLocations`) |
| 탐색기 열기 | 폴더는 그 폴더를, 파일은 그 파일을 선택한 채로 탐색기를 연다. 지우거나 옮기는 일은 사용자가 탐색기에서 직접 한다 |

구현 원칙:

- 링크·정션은 따라가지 않는다. 따라가면 같은 공간을 두 번 센다(예: `C:\Users\All Users` → `C:\ProgramData`).
- OneDrive처럼 내용 없이 자리만 있는 클라우드 파일은 디스크 공간을 쓰지 않으므로 크기에 넣지 않는다.
- 열 수 없는 폴더는 크기에 들어가지 않으며 개수를 따로 보여 준다. Windows 폴더는 하드 링크 때문에 실제보다 크게 보일 수 있다. 그래서 "분석한 크기"와 "드라이브 사용 중"이 다를 수 있음을 화면에 적는다.
- 폴더를 여러 스레드(최대 8개)로 나눠 읽는다. 폴더가 수십만 개라 경로 문자열은 저장하지 않고 필요할 때 만든다.
- 하위 폴더가 300개를 넘으면 큰 것 300개만 따로 보여 주고 나머지는 한 줄로 묶는다.

### 3.2 메모리 (`WinCleaner.Memory`)

Windows는 남는 RAM을 캐시로 쓰는 것이 정상이다. 사용량 숫자만 줄이면 오히려 느려질 수 있으므로 **원인 파악이 우선이고, 정리는 수동으로만** 한다.

| 기능 | 방법 | 비고 |
|---|---|---|
| 메모리 현황 | `GetPerformanceInfo` | 사용 중, 사용 가능, 캐시(대기 목록 + 시스템 작업 집합), 커밋(확보·한도). **구현됨** |
| 프로그램별 사용량 | `Process.GetProcesses` 스냅숏의 작업 집합·전용 바이트 | 같은 실행 파일끼리 묶어(Chrome 22개 → 한 줄) 많이 쓰는 순으로 정렬. 실행 파일 설명("Google Chrome")을 이름으로 보여 준다. 화면이 보이는 동안 3초마다 갱신. **구현됨** |
| 작업 집합 비우기 | `EmptyWorkingSet` | 사용자가 고른 프로그램에만, 확인 창을 거쳐 실행. 프로세스는 종료되지 않는다. Idle·System은 제외. **구현됨** |
| 대기 목록 비우기 | `NtSetSystemInformation(SystemMemoryListInformation, MemoryPurgeStandbyList)` | 게임 끊김 같은 특수 상황용. 관리자 토큰의 `SeProfileSingleProcessPrivilege`를 켜서 실행하고, 줄어든 캐시 크기를 보여 준다. **구현됨** |

자동 반복 정리(RAM 부스터)는 넣지 않는다.

### 3.3 시스템 최적화 (`WinCleaner.Optimizer`)

모든 항목은 `적용`과 `되돌리기`를 한 쌍으로 구현하고, 현재 적용 상태를 읽을 수 있어야 한다.

| ID | 항목 | 내용 | 위험도 | 재시작 |
|---|---|---|---|---|
| `startup.manage` | 시작 프로그램 관리 | Run 레지스트리(HKCU, HKLM, HKLM 32비트)와 시작 폴더 항목을 켜고 끈다. 작업 관리자와 같은 방식(`Explorer\StartupApproved` 값)이라 항목을 지우지 않고, 작업 관리자와 상태가 맞는다. **구현됨.** 작업 스케줄러 항목은 아직 | 낮음 | 다음 로그인부터 |
| `power.plan` | 전원 옵션 | PC에 있는 전원 관리 옵션 목록에서 골라 바꾼다. PC마다 "고성능" GUID가 달라(복제한 구성 등) 고정 GUID를 쓰지 않는다. **구현됨** | 낮음 | 필요 없음 |
| `visual.effects` | 시각 효과 | 창·메뉴·콤보 상자 애니메이션, 부드러운 스크롤, 툴팁·선택 페이드, 커서·창 그림자, 창 안 애니메이션 9가지를 끈다. 글꼴 다듬기와 미리보기 그림은 둔다. 현재 사용자에게만 바로 적용된다. **구현됨** | 낮음 | 필요 없음 |
| `background.apps` | 백그라운드 앱 | 스토어 앱의 백그라운드 실행 제한 | 낮음 | 필요 없음 |
| `search.index` | 검색 인덱싱 | 인덱싱 범위 축소 | 중간 | 필요 없음 |
| `drive.optimize` | 드라이브 최적화 | `defrag <드라이브>: /O`로 매체에 맞게 실행한다(SSD는 TRIM, HDD는 조각 모음). 진행률을 보여 주고 취소할 수 있다. 관리자 필요. **구현됨** | 낮음 | 필요 없음 |
| `disk.health` | 디스크 건강 상태 | 저장소 WMI(`MSFT_PhysicalDisk`)로 모델, SSD/HDD, 연결 방식, 건강 상태를 읽는다 (읽기 전용, 일반 권한 가능). **구현됨** | 없음 | 필요 없음 |
| `services.safe` | 불필요한 서비스 | 검증된 소수 목록만 다루며 기본값은 꺼짐 | 높음 | 필요할 수 있음 |
| `hibernate` | 최대 절전 끄기 | `powercfg /hibernate off`로 hiberfil.sys(약 RAM의 40%)를 없앤다. 최대 절전 모드와 빠른 시작도 꺼진다. 되돌리면 켜고, 원래 hiberfil 종류(reduced/full)도 되살린다. **구현됨** | 중간 | 필요 없음 |

### 3.4 안전장치 (`WinCleaner.Safety`)

1. **실행 흐름 고정**: 스캔 → 미리보기 → 선택 → 실행 → 결과 보고. 스캔하자마자 지우는 경로는 만들지 않는다.
2. **시스템 복원 지점**: 위험도 "주의" 이상인 최적화 항목(현재 최대 절전 끄기)을 적용하기 전에 WMI `SystemRestore.CreateRestorePoint`로 만든다. 최적화 화면의 체크박스로 끌 수 있고 기본값은 켜짐이다. 시작 프로그램·전원 옵션·시각 효과처럼 가벼운 설정은 복원 지점 없이 변경 기록만으로 되돌린다. 바꿀 때마다 복원 지점을 만들면 C: 공간만 쓰기 때문이다.
   - Windows는 24시간에 한 번만 새로 만들고 그 안의 요청은 오류 없이 무시한다. 그래서 먼저 목록을 보고, 24시간 안의 복원 지점이 있으면 그것을 쓴다고 알린다.
   - 만들지 못하면(시스템 보호 꺼짐, 오류) 이유를 보여 주고 계속할지 묻는다.
   - 파일 정리 전에는 만들지 않는다. 복원 지점은 사용자 파일을 되살리지 못하므로, 파일 정리는 미리보기·확인 창·"주의" 표시로 보호한다.
   - 기록 화면에서 직접 만들거나 Windows 시스템 복원(`rstrui.exe`)을 열 수 있다.
3. **변경 기록**: 모든 일을 `%LOCALAPPDATA%\WinCleaner\journal.json`에 남긴다(`ChangeJournal`, 최근 500개).
   - 기록하는 일: 정리, 설정 변경, 되돌림, 복원 지점.
   - 설정 변경은 바꾸기 전 값(`TweakBackup`)을 함께 저장하고, 기록 화면이나 최적화 화면에서 그 값으로 되돌린다. 기록이 없으면 Windows 기본값으로 되돌린다.
   - 정리는 기록 파일 경로와 함께 남기되 "되돌릴 수 없음"으로 표시한다.
   - 기록 파일은 사용자 폴더에 있어 다른 프로그램이 바꿀 수 있다. 그래서 되돌릴 때 각 항목은 백업 값을 그대로 쓰지 않고, 아는 값인지 검사한 뒤 모르는 값은 Windows 기본값으로 처리한다.
   - 파일이 깨져 있으면 옆에 따로 보관하고 새로 시작한다. 쓰다가 꺼져도 깨지지 않게 임시 파일에 쓴 뒤 바꿔 끼운다.
4. **허용 경로만 삭제**: 규칙에 정의된 경로 아래만 지운다. 심볼릭 링크와 정션(재분석 지점)은 따라가지 않는다. 정해진 경로 밖의 파일이 지워지는 사고는 대부분 이런 링크 때문에 생긴다.
5. **사용 중인 파일은 건너뜀**: 실패는 로그에만 남기고 전체 작업은 계속한다.
6. **관리자 권한 확인**: 관리자가 아니면 시스템 영역 규칙은 스캔만 하고 정리는 막는다.
7. **보호 폴더 검사(`PathGuard`)**: 규칙이 잘못됐거나 `%TEMP%`가 엉뚱한 곳을 가리켜도 다음 폴더는 정리 대상이 될 수 없다.
   - 드라이브 최상위 폴더
   - Windows, System32, WinSxS, Program Files, ProgramData, 사용자 프로필, AppData 자체와 그 상위 폴더
   - 바탕 화면, 문서, 사진, 음악, 동영상, 다운로드, OneDrive와 그 안의 모든 폴더
8. **정리 직전 다시 확인**: 스캔 결과를 그대로 믿지 않는다. 지우기 직전에 각 파일이 정리 대상 폴더 안에 있는지(`..` 경로 포함), 거치는 폴더에 링크가 없는지, 스캔 때와 수정 시각이 같은지 다시 확인한다.
9. **빈 폴더 정리 범위**: 파일을 지워서 비게 된 폴더만 지운다. 정리 대상 폴더 자체와 기준 시간보다 최근에 만든 폴더는 남긴다.
10. **규칙은 프로그램 안에 포함**: 관리자 권한으로 도는 앱이 바깥 파일을 읽어 지울 대상을 바꾸지 못하도록, 규칙 파일은 빌드할 때 프로그램 안에 넣는다.

### 4.2 핵심 인터페이스

모든 기능은 아래 두 인터페이스 중 하나로 통일한다. 기능을 추가하기 쉽고, 안전장치를 한곳에서 적용할 수 있다.

```csharp
public interface ICleanupRule
{
    string Id { get; }
    string Name { get; }
    string Description { get; }
    string Category { get; }
    RiskLevel Risk { get; }
    bool RequiresElevation { get; }
    Task<ScanResult> ScanAsync(CancellationToken ct);
    Task<CleanResult> CleanAsync(ScanResult selected, CancellationToken ct);  // 취소되면 그때까지의 결과를 돌려줌
}

public sealed record ScanItem(string Path, long SizeBytes, DateTime LastWriteTimeUtc);
public sealed record ScanResult(string RuleId, IReadOnlyList<ScanItem> Items, IReadOnlyList<string> Warnings);
public sealed record CleanResult(string RuleId, IReadOnlyList<ScanItem> Deleted, IReadOnlyList<SkippedItem> Skipped);

public interface ITweak
{
    string Id { get; }
    string Name { get; }
    string Description { get; }
    RiskLevel Risk { get; }
    bool RequiresElevation { get; }
    bool RequiresRestart { get; }
    Task<TweakState> GetStateAsync(CancellationToken ct);        // 적용 여부와 "켜짐 · 6.3 GB" 같은 상태 문구
    Task<TweakBackup> ApplyAsync(CancellationToken ct);          // 바꾸기 전 값을 돌려줌 → 변경 기록에 저장
    Task RevertAsync(TweakBackup? backup, CancellationToken ct); // 백업 값으로, 없으면 Windows 기본값으로
}
```

### 4.3 청소 규칙 정의 (`rules/cleanup-rules.json`)

파일·폴더를 지우는 규칙은 코드 대신 JSON으로 정의하고, `FileCleanupRule` 하나가 모든 규칙을 실행한다. 새 대상을 추가할 때는 JSON만 고치고 다시 빌드하면 된다.

```json
{
  "id": "browser.chrome",
  "name": "Chrome 캐시",
  "description": "웹 페이지를 빨리 열려고 저장해 둔 파일",
  "category": "브라우저",
  "risk": "Low",
  "requiresElevation": false,
  "minAgeHours": 0,
  "skipIfRunning": [ "chrome" ],
  "targets": [
    { "path": "%LOCALAPPDATA%\\Google\\Chrome\\User Data\\*\\Cache", "pattern": "*", "recursive": true }
  ]
}
```

- `path`: 환경 변수와 폴더 이름의 `*`를 쓸 수 있다. `*`는 실제 폴더로 펼치되 링크 폴더는 뺀다.
- `pattern`이 와일드카드 없는 파일 이름이고 `recursive`가 false이면(예: `MEMORY.DMP`) 그 파일 하나만 가리킨다. 이때만 보호 폴더 안을 대상으로 삼을 수 있다.

  - 휴지통: 내용 파일이 없어 "정리할 파일 없음"
  - 기록: 비어 있음

**아직 실제로 확인하지 못한 것**: 관리자 권한이 필요한 동작은 테스트 대역으로만 검증했다. 처음 관리자로 쓸 때 확인이 필요하다.

- WMI로 복원 지점 만들기·읽기
- `powercfg`로 최대 절전 끄기·켜기
- 실제 휴지통 항목 지우기

**보류**: `dism.component`(업데이트 잔여 구성 요소)는 실행에 수십 분이 걸리고 되돌릴 수 없어 6단계로 둔다. `windows.old`는 이 PC에 없다.

### 5.5 4단계 결과 (최적화)

- 시작 프로그램(`Optimizer.Startup`): `StartupManager`(목록), `RegistryStartupStore`(레지스트리·시작 폴더), `StartupEntryTweak`(항목 하나 끄기).
  - 항목마다 게시자, 실행 명령, 등록 위치를 보여 준다.
  - 실행 파일이 없는 항목은 "지운 프로그램의 남은 항목일 수 있음"으로 알린다.
  - 모든 사용자 항목은 관리자 권한일 때만 바꿀 수 있다.
- 시작 프로그램 항목은 PC마다 다르므로, 변경 기록의 ID(`startup:<위치>:<이름>`)에서 항목을 다시 만들어 기록 화면에서도 되돌린다(`TweakCatalog`). 전원 관리 옵션도 같은 방식이다.
- 전원 관리 옵션(`PowerPlanTweak`): powrprof.dll로 목록·현재 옵션을 읽고 바꾼다. 되돌릴 때는 기록에 남은 옵션이 이 PC에 실제로 있을 때만 쓰고, 없으면 "균형 조정"으로 돌아간다.
- 시각 효과(`VisualEffectsTweak`): `SystemParametersInfo`로 9가지 효과의 원래 값을 하나씩 백업하고 되돌린다.
- 드라이브(`DriveMaintenance`): 저장소 WMI로 드라이브 정보를 읽고, `defrag /O /U`로 최적화한다. 콘솔 출력은 OEM 코드 페이지(한국어 949)로 읽어 진행률 문구가 깨지지 않게 했다. 최적화 결과는 변경 기록에 "유지 관리"로 남는다.
- 최적화 화면은 탭 3개(시작 프로그램, 설정, 드라이브)로 나눴다.
- 테스트 124개 통과, 빌드 경고 0개.
- 실제 PC(일반 권한)에서 확인한 것:
  - 시작 프로그램 24개(켜짐 10, 꺼짐 14)를 작업 관리자와 같은 상태로 읽었다.
  - 전원 관리 옵션 목록과 현재 옵션("균형 조정")을 읽었다.
  - 시각 효과 9개 중 8개가 켜져 있다.
  - C:는 SSD, D:는 HDD이고 둘 다 상태 정상이다.
- 화면을 확인하다가 고친 버그: 스위치가 켜진 항목도 꺼진 모양으로 그려졌다. 템플릿 트리거가 버튼 자신이 아니라 바깥 템플릿을 보고 있었고, bool 값을 문자열 "True"와 비교하고 있었다.

**아직 실제로 확인하지 못한 것**: 시작 프로그램·전원 옵션·시각 효과를 실제로 바꾸는 동작과 드라이브 최적화 실행. 모두 테스트 대역으로만 검증했다.

### 5.6 5단계 결과 (메모리)

- `WinCleaner.Memory`: `WindowsMemoryService`(현황, 프로세스 목록, 실행 파일 설명, 작업 집합 비우기, 대기 목록 비우기)와 `ProcessGrouping`(실행 파일별 묶기).
- 메모리 화면:
  - 화면이 보이는 동안에만 3초마다 다시 읽고(`PeriodicTimer`), 다른 화면으로 가면 멈춘다.
  - 목록은 통째로 바꾸지 않고 항목을 갱신·이동해서, 다시 읽어도 스크롤과 체크가 풀리지 않는다.
- 작업 집합 비우기와 대기 목록 비우기는 변경 기록에 "유지 관리"로 남는다. 되돌릴 대상은 없다.
- 쓰지 않게 된 "준비 중" 안내 화면(`PlaceholderViewModel`)을 지웠다. 이제 모든 메뉴가 실제 기능이다.
- 테스트 135개 통과, 빌드 경고 0개. 실제 시스템 테스트는 테스트 프로세스 자신만 정리하고, 대기 목록 비우기는 일반 권한에서 거절되는 것만 확인한다.
- 실제 PC(일반 권한)에서 확인한 것:
  - 사용 중 12.6 / 15.9GB, 사용 가능 3.3GB, 캐시 3.7GB, 커밋 15.1 / 18.2GB
  - 가장 많이 쓰는 프로그램: Chrome(프로세스 22개, 2.9GB), Claude(14개, 2.6GB)
  - 일반 권한에서는 대기 목록 비우기 버튼이 막히고, 프로그램을 고르기 전에는 작업 집합 비우기 버튼이 막힌다.
- 커밋이 한도의 83%다. 한도에 닿으면 메모리 부족 오류가 나므로, 브라우저 탭을 줄이거나 페이지 파일 크기를 늘리는 것이 작업 집합 비우기보다 근본적인 대책이다.

**아직 실제로 확인하지 못한 것**: 관리자 권한에서의 대기 목록 비우기. 작업 집합 비우기는 테스트 프로세스 자신에게만 실제로 실행해 봤다.

### 5.7 실행 환경 문제와 해결 (2026-10-25)

1단계에서 .NET SDK를 사용자 폴더에만 설치했더니, 빌드는 됐지만 실행 파일을 더블클릭하면 "You must install .NET Desktop Runtime" 오류가 났다. 개발 중 확인은 스크립트 안에서 `DOTNET_ROOT`를 직접 지정하고 일반 권한으로만 실행했기 때문에 이 문제를 놓쳤다.

- 해결: Microsoft 서명을 확인한 .NET 10 Desktop Runtime 10.0.13을 PC 전체(`C:\Program Files\dotnet`)에 설치했다. `DOTNET_ROOT` 없이 실행해 PC 전체 런타임을 쓰는 것을 확인했고, 사용자가 더블클릭과 UAC 승인으로 실행되는 것도 확인했다.
- 더 이상 필요 없는 사용자 환경 변수 `DOTNET_ROOT`는 지웠다. `dotnet` 명령(빌드용 SDK)은 계속 사용자 폴더의 SDK를 쓴다.
- README에 "문제 해결" 항목을 추가했다.

## 6. 테스트 전략

- **단위 테스트**: 규칙 엔진, 경로 필터, 크기 계산은 임시 폴더에 가짜 파일 트리를 만들어 검증한다.
- **읽기 전용 기능**(스캔, 현황 표시)은 실제 PC에서 바로 확인한다.
- **삭제·설정 변경 기능**은 Windows Sandbox에서 먼저 검증한 뒤 실제 PC에서 실행한다. Windows Sandbox는 Windows 10 Pro의 선택적 기능이라 한 번 켜 줘야 한다.

---

## 7. 미결 사항

- 코드 서명 인증서를 쓸지 정해야 한다. 서명이 없으면 처음 실행할 때 SmartScreen 경고가 뜬다.
- 배포 방식: .NET 런타임 포함(self-contained, 약 70MB 이상) 또는 런타임 별도 설치(framework-dependent, 수 MB).

## 8. 개발 환경

| 항목 | 내용 |
|---|---|
| .NET SDK | 10.0.402, 관리자 권한 없이 `%LOCALAPPDATA%\Microsoft\dotnet`에 설치 (Microsoft 공식 `dotnet-install.ps1`, 약 0.75GB) |
| 환경 변수 | 사용자 `PATH`에 위 폴더 추가. (`DOTNET_ROOT`는 PC 전체 런타임을 설치한 뒤 지웠다. 5.7 참고) |
| 실행용 런타임 | .NET 10 Desktop Runtime 10.0.13, PC 전체(`C:\Program Files\dotnet`) |
| NuGet 패키지 | CommunityToolkit.Mvvm 8.4.2, System.Management 10.0.13, xUnit 2.9.3 |
| 정리 기록 | `%LOCALAPPDATA%\WinCleaner\logs` |
| 변경 기록 | `%LOCALAPPDATA%\WinCleaner\journal.json` |

명령 (새 터미널에서 실행해야 `PATH`가 반영된다):

```bash
dotnet build WinCleaner.slnx
dotnet test WinCleaner.slnx
```

실행 파일은 `src\WinCleaner.App\bin\Debug\net10.0-windows\WinCleaner.exe`이다. 실행하면 UAC 창이 뜬다. 설치부터 실행까지의 순서는 [README](../README.md)에 정리했다.
